Engineering • Multi-Agent Delivery • Evidence Gates

Govern software work from issue to production proof.

The OMOS Engineering Council is the development-governance lifecycle used to coordinate approved engineering agents and repositories without confusing agent activity, green tests, merges, deployment, or production verification.

Canonical lifecycle

Issue → Classify → Assign → Implement → Pull Request → Independent Review → Tests / CI / Security → OMOS Review → Human Approval → Merge → Deploy → Deployment Proof → Engineering Record

Required controls

  • The authoring agent cannot be the sole final reviewer of its own change.
  • Green CI is required where applicable but is not sufficient proof of architectural correctness or deployment.
  • Consequential merges and production changes remain human-authorized.
  • A merge is not task completion; the intended revision and behavior must be proven in the target environment.
  • Secrets, fabricated evidence, and unsupported Production labels are prohibited.

Engineering Record

Significant changes should retain issue, repository, assigned agent, branch, pull request, reviewers, test/security results, human approval, merged SHA, deployed SHA, environment, verification evidence, rollback reference, and final maturity state.

OMOS and ACC

OMOS governs reasoning, Decision Records, architecture boundaries, and evidence state. ACC is the operational console for agents, tasks, queues, workflows, approved execution, and system supervision. GitHub and runtime infrastructure remain technical systems of record; human authority remains separate.

Developer agents

Developer roles can include architecture, implementation, adversarial review, verification, security, deployment, documentation, and engineering coordination. Binding a named product or agent to a role requires separate operational evidence.
