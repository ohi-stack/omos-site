Developer Agents • Roles • Separation of Duties

Agents can perform engineering work; they do not self-authorize production.

OMOS maintains a developer-agent operating model for architecture, implementation, QA/testing, independent review, security, deployment, documentation, and engineering coordination. Named tools can be bound to those roles only when the binding is actually configured and verified.

Role classes

Architecture · Builder / Implementation · QA / Test · Independent Review · Security · Deployment · Documentation · OMOS Engineering Coordination

Core rules

  • Least privilege by default.
  • No developer agent should push consequential changes directly to protected production state without the required workflow.
  • The authoring agent cannot be the sole final reviewer.
  • Tests and security findings must be recorded rather than summarized away.
  • Human approval remains the authorization boundary for consequential merge/deployment actions.
  • Deployment proof must identify what revision and behavior actually reached the target environment.

Tool bindings

Codex, GitHub engineering automation, Antigravity, and future developer systems may participate through approved task/evidence envelopes and repository workflows. A listed tool is not automatically connected merely because the role exists in the registry.

ACC relationship

ACC is the operator console for registering agents, assigning work, observing tasks/queues/workflows, and supervising approved execution. OMOS supplies governance and evidence discipline around the engineering lifecycle.
