Council Integrity • Provenance Before Synthesis

OMOS must know who produced an output before it compares the output.

Provider attribution is a data-integrity requirement. A label typed or relayed by a person is useful context, but it is not mechanical proof that the content came from the named provider. OMOS therefore treats provenance as a prerequisite to trustworthy Council synthesis.

Contribution envelope

A production-grade Council contribution should carry a contribution ID, run ID, phase, assigned role, provider, model, connector identity, provider request ID when available, input hash, output hash, timestamps, latency, simulation state, provenance state, raw output reference or captured output, and execution metadata.

Provenance states

  • verified_runtime_capture — output was captured through the runtime execution path with supporting metadata.
  • simulated — output was generated by an explicit simulation path.
  • human_relay_unverified — content was manually transferred and the provider identity is asserted, not mechanically proven.
  • disputed — authorship or origin has been challenged.
  • unresolved — available evidence cannot establish the source.

Integrity rule

Authenticate → Invoke → Capture → Attribute → Hash → Normalize → Decompose → GCD → Contradictions → Evidence → Verification → Governed Synthesis.

If attribution is disputed, OMOS should preserve the original assertion and the later correction as revisions rather than silently rewriting history.

Current implementation boundary

This is the Council integrity standard. The current runtime already records provider/model/simulation metadata, but complete contribution-level provenance hardening remains an implementation track and should not be presented as fully Production until its runtime fields and regression tests are merged, deployed, and verified.
