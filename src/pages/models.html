OLLM Overview

Important connector distinction

Developer app connections are not OMOS runtime connectors.

Connecting GitHub, Drive, Stripe, Supabase, WordPress, or other tools inside ChatGPT, Claude, Gemini, Codex, Antigravity, or another developer application can help build and review OMOS. Those connections do not automatically make that model or service a live OMOS Council provider.

For manual copy-and-paste between consumer chat applications to disappear, OMOS itself must hold a server-side provider connection to each authorized model API, test that connection, normalize its response, record provenance, and expose its health without exposing credentials.

Runtime target: OpenAI ↔ OMOS · Anthropic ↔ OMOS · Gemini ↔ OMOS · xAI ↔ OMOS. Each Council run should record which providers were requested, configured, completed, failed, simulated, degraded, and actually used.

Connection testing and health target

A production connector should distinguish configuration from execution. The target health vocabulary is CONNECTED, NOT_CONFIGURED, DEGRADED, and UNAVAILABLE. OMOS should expose safe per-provider connection tests, active model identity, last health check, latency, usage metadata where available, sanitized errors, and provider request/provenance identifiers.

The planned operational API family is GET /api/v1/connectors/models, GET /api/v1/connectors/models/:provider, and authenticated POST /api/v1/connectors/models/:provider/test. Until those live request tests are implemented and deployed, the current provider API should be read as configuration/runtime-availability metadata rather than verified connectivity.

GPT-6 Astra authorization boundary

Source support for Astra capabilities does not automatically authorize web search, file search, code execution, computer use, hosted shell access, or MCP activity. Those capabilities remain explicitly gated through OMOS connection/adaptation policy and human approval where required.

Normalized provider contract

A production-grade connector should report provider, model, capabilities, availability, health, authentication state without exposing secrets, invoke/stream/review/retry/cancel behavior, latency, token or usage data, estimated cost where supported, provider request ID, errors, and provenance. Provider configuration alone is not proof of a successful live request.

Graceful degradation

If a requested provider fails, OMOS should not silently substitute it. The run should record requested providers, completed providers, failed providers, and a DEGRADED Council state where appropriate. Human review remains required when the failure materially changes the result.

Security boundary

Provider API keys and credentials remain server-side. Browser pages may display connection state and non-sensitive health metadata, but must never receive raw provider secrets.

Connection architecture

Model Gateway = who OMOS reasons with. Data / Action / Environment Gateway = what OMOS can securely read, invoke, synchronize, or operate. These remain separate authorization surfaces even when both use common adapter patterns.
